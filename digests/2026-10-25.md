## 本周要点

本周最值得关注的是 StaGPO：它承认真实用户常常“话说不全”，让智能体显式记录任务所需信息与缺口，并按相同对话状态分组比较 rollout，在弱用户设定下的 τ²-bench、ToolWOZ 上都优于 GRPO。工程侧，SchemaShield-Lite 用免训练的“规范化 + 校验 + 一次受约束修复”扛住工具接口漂移，AKV 则让智能体直接编辑自己的 KV 缓存来替代摘要压缩，降本约 28%。训练侧还有两条清晰信号：在多种 harness 上做 RL 能迁移到未见过的 harness（包括 Claude Code），Meta 开源的 Muse Glimmer 30B 则给出了一份完整的端侧智能体后训练配方。

## 1. 不是每个用户都把话说全：在非理想模拟用户下训练工具智能体（StaGPO）

- 链接：[arXiv:2610.24294](https://arxiv.org/abs/2610.24294)
- 来源 / 日期：arXiv，2026-10-16
- 主题：agent_finetuning · tool_calling ｜ 相关度：**5/5**

**摘要：** 作者通过遮盖用户回复中的部分句子构造“弱”模拟用户，发现所有策略面对这类用户都会退化，而单纯用弱用户训练、或提示智能体多追问，都没有带来超出噪声的提升。为此提出 StaGPO：智能体在每轮显式写出任务需要什么、还缺什么、正在如何补齐，GRPO 再在到达相同状态的 rollout 之间比较各轮，从而得到步级信用；训练流程是少量 SFT 冷启动加 RL。在 ToolWOZ 弱用户设定下，Qwen3.5-2B 达到 76.8%，比 GRPO 高 4.8 个点；τ²-bench 上两个尺寸都是最佳，但 4B 的优势较小。暂未见代码。

**可借鉴之处：** 企业用户的需求描述往往不完整——评测与 RL 环境里应加入“信息残缺”的模拟用户，并让模型显式维护“已知/缺失”槽位，这既是信用分配的抓手，也便于审计。

## 2. 接口漂移下的鲁棒函数调用：SchemaShield-Lite

- 链接：[arXiv:2610.23342](https://arxiv.org/abs/2610.23342) ｜ 代码：[AniruddhaChattopadhyay/tool-drift](https://github.com/AniruddhaChattopadhyay/tool-drift)
- 来源 / 日期：arXiv，2026-10-16
- 主题：tool_calling · enterprise_agents ｜ 相关度：**5/5**

**摘要：** 研究部署后工具描述、参数 schema 或候选工具列表发生变化、但工具行为不变的“接口漂移”。SchemaShield-Lite 是一个免训练的推理时层：把工具描述规范化为统一的“工具卡”，对调用做确定性 schema 校验，工具名缺失时从候选集重选，并只做一次受约束修复。Qwen3.5-9B 在 200 条 BFCL 漂移样本上准确率从 0.580 升到 0.805，在 DICE-BENCH 300 条样本上从 0.717 升到 0.813，而朴素重试只到 0.610 / 0.727；Qwen3.5-35B-A3B 在 BFCL 上从 0.635 升到 0.845，且修复没有破坏任何原本正确的样本。

**可借鉴之处：** ERP 接口频繁版本升级，在模型与 API 之间加一层“工具卡规范化 + 确定性校验 + 单次修复”，几乎零成本就能挡住大部分因 schema 变化引发的失败，也可用其漂移脚本做回归测试。

## 3. Harness 规模化：让智能体 RL 泛化到未见过的执行框架

- 链接：[arXiv:2610.29458](https://arxiv.org/abs/2610.29458)
- 来源 / 日期：arXiv，2026-10-21
- 主题：agent_finetuning ｜ 相关度：**4/5**

**摘要：** 作者把 harness 拆成系统提示、工具接口、观测格式、上下文管理和工作流五个部件，训练时在多种组合的平衡子集上做 RL，并为每个任务配上结构相近的 harness。在 ClawGym-Task（1.35 万任务）上训练后，Qwen3-4B 用 GRPO 在三个基准上的平均分从 29.81 提升到 39.04，Qwen3-30B-A3B 从 37.29 提升到 42.78，PPO 同样受益。更关键的是能迁移到未见过的外部 harness：在 Claude Code 中 4B / 30B 分别得到 37.22 / 41.20，高于直接在该 harness 上做 SFT 或 RL 的结果。暂未见代码。

**可借鉴之处：** 若模型要接入多个内部智能体框架，训练时应主动随机化提示模板、工具格式和上下文策略，而不是只在一套 harness 上过拟合。

## 4. 面向智能体的缓存工程（AKV）

- 链接：[arXiv:2610.28577](https://arxiv.org/abs/2610.28577) ｜ 代码：[thu-nics/AKV](https://github.com/thu-nics/AKV)
- 来源 / 日期：arXiv，2026-10-20
- 主题：quantization_inference ｜ 相关度：**4/5**

**摘要：** 与其截断或摘要上下文（迫使模型重算整段提示），不如让智能体直接编辑自己的 KV 缓存：把某些条目排除在后续注意力之外，并平移保留键的位置编码。配套的 AKV 服务引擎提供无状态 API，内部处理缓存复用、驱逐与恢复——因为相同 token 在不同缓存操作序列下会产生不同的缓存状态。“滚动丢弃旧工具返回”的策略比“超长即摘要”平均高 1.7 分、成本低 27.7%，吞吐最多提升 1.2 倍、P95 延迟改善 1.5 倍；系统自我改进的策略还能比专家设计再省 7.1%。

**可借鉴之处：** 企业智能体的上下文大头往往是冗长的工具返回（查询结果、单据 JSON），按“过期工具输出”做缓存级驱逐比反复摘要更省、更稳。

## 5. EGI-BENCH：企业通用智能基准套件

- 链接：[arXiv:2610.27234](https://arxiv.org/abs/2610.27234) ｜ 代码：[SalesforceAIResearch/egi-bench](https://github.com/SalesforceAIResearch/egi-bench)
- 来源 / 日期：arXiv，2026-10-19
- 主题：enterprise_agents · evaluation ｜ 相关度：**4/5**

**摘要：** Salesforce AI Research 把 CRMArena、HERB、PersonaBench、UserBench、MCP-Universe、MCPEval、BenchForce、LocoBench 八个企业智能体基准统一到一个命令行工具下，提供固定运行预算的 quick / deep 两种模式，并在六个能力维度上汇总出 EGI 分数。quick 模式下 14 个闭源模型的 EGI 从 39.6 到 65.6 不等，且没有模型在所有维度领先：有的长于结果与规划，有的长于工具执行与安全拒答。论文只报告了闭源模型，但框架开源，可直接跑开源模型。

**可借鉴之处：** 把自研模型放进这类“多基准 + 能力维度”的统一面板，比单看某一个排行榜更能暴露短板（例如工具执行强但检索落地弱）。

## 6. Muse Glimmer 30B：开源端侧智能体模型

- 链接：[arXiv:2610.24628](https://arxiv.org/abs/2610.24628) ｜ 权重：[meta-models/Muse-Glimmer-30B](https://huggingface.co/meta-models/Muse-Glimmer-30B)
- 来源 / 日期：arXiv，2026-10-17（Meta Superintelligence Labs）
- 主题：agent_finetuning ｜ 相关度：**4/5**

**摘要：** 约 29.6B 的稠密模型，预训练阶段蒸馏 Muse Spark 教师的 logits，随后进行加入工具使用轨迹的智能体中训练并扩展到 128K 上下文。后训练依次为 SFT、按奖励过滤的教师 rollout、on-policy 蒸馏，以及结合奖励模型与验证器的多目标 RL；合成数据来自带 mock 应用（邮件、日历、类 GitHub 工具）和可验证评分规则的模拟“宇宙”。在 MCPAtlas、τ³-Banking、GAIA2 上优于 Gemma4-31B 与 Qwen3.6-27B，但在 SWE-Bench Verified、OSWorld、TerminalBench 上落后于 Qwen3.6-27B；以 Apache 2.0 开放，附 4-bit 版本与投机解码头。

**可借鉴之处：** 这份配方（教师 logit 蒸馏 → 智能体中训练 → 拒绝采样 + on-policy 蒸馏 → 多目标 RL）可以作为 30B 级企业智能体后训练的参照模板；mock 应用 + 可验证评分规则的环境构建方式也易于迁移。

## 7. Self-Credit：用组内重缩放做长程智能体 RL 的信用分配

- 链接：[arXiv:2610.28388](https://arxiv.org/abs/2610.28388)
- 来源 / 日期：arXiv，2026-10-20
- 主题：agent_finetuning ｜ 相关度：**4/5**

**摘要：** 策略在推理中撰写摘要并引用包含关键证据的早期轮次；方法再对比同一提示下成功与失败的 rollout，对被引用轮次的优势进行重新加权，把稀疏结果奖励变成更稠密的信用信号。在 BrowseComp-Plus 上，相对 Qwen3-8B / Qwen3-32B 基座分别提升 37.0 / 36.2 个点，并比最强的智能体 RL 基线高 8.5 / 5.6 个点；GAIA 与 xBench-DeepSearch 上也各有约 5 个点的提升。暂未见代码。

**可借鉴之处：** 长流程任务可以让模型自己标注“哪一步拿到了关键证据”，再据此分配优势——比训练单独的过程奖励模型便宜得多。本条与上期 [Tev](2026-10-18.md) 的稠密进度奖励思路互补。

## 8. SANE：面向 LLM 评审的自动化、按评分器定制的蜕变测试

- 链接：[arXiv:2610.28886](https://arxiv.org/abs/2610.28886)
- 来源 / 日期：arXiv，2026-10-20
- 主题：evaluation ｜ 相关度：**4/5**

**摘要：** 针对某个具体的 LLM 评审或评分器，自动生成“蜕变测试族”——对输入做受控改动，并预先知道分数应如何变化。在五个领域中，SANE 产出的已验证测试族是 Judge Reliability Harness 的 3.7 倍，有效性相当，并在每个领域都发现了评分器弱点（后者在专业性、毒性两个领域一个也没找到）。在忠实度任务上，SANE 对 11 个评审模型的排序与人工标注的 FaithBench 高度一致（Spearman ρ≈0.85，对照方法约 0.10）。暂未见代码。

**可借鉴之处：** 上线 LLM-as-judge 做回归评测前，先用蜕变测试检验评审本身是否对关键改动敏感，再决定能否信它的分数。延续了上期[评审一致性](2026-10-18.md)的话题。

## 框架更新

- **TRL v1.16.0**（2026-10-15）：AsyncGRPO 以前缀树方式打包微批，训练最多快约 3.1 倍；异步训练器支持 AMD GPU；工具调用参数可按 JSON schema 定型。**行为变更**：`pad_to_multiple_of` 默认改为 `"auto"`。另补上期未能核实的 **v1.15.0**（10-08）：SFT/DPO/KTO/GRPO/RLOO/蒸馏默认启用融合 LM head，不再构造完整 logits 张量，最大序列长度最多提升约 6.9 倍、峰值显存降 52–82%；**破坏性变更**：对 `lm_head` 挂 PEFT 适配器会报错，`use_liger_kernel=True` 计划在 v2.0.0 移除。（[Releases](https://github.com/huggingface/trl/releases)，据 PyPI 与第三方发布追踪整理）
- **llama.cpp v0.7.0**（2026-10-15）：新增 MoE 专家的 GPU 缓存（`--moe-cache-mib`，解码最多约 2.2 倍）、新的投机解码方式与 GLM5-Next 的 MTP 解码；修复 CUDA MMQ 越界、CUDA/HIP flash-attention 竞争等多处内核问题。**破坏性变更**：server 默认端口由 8080 改为 9931（Docker 镜像仍为 8080），聊天输出改为分段数组，符号默认隐藏。（[发布说明](https://github.com/ggml-org/llama.cpp/releases/tag/v0.7.0)，据第三方发布追踪整理；上期误报“窗口内无新版本”，特此更正）
- **vLLM**：窗口内仅有 v0.32.1rc0 预发布，无正式版（上期已覆盖 [v0.32.0](2026-10-18.md)）。
- **llm-compressor 0.14.0.1**（2026-10-22，PyPI）：看起来是补丁版本，未取得发行说明。
- verl、LLaMA-Factory：窗口内无新版本。本期 GitHub Releases 页面无法直接抓取，以上均来自 PyPI 与第三方追踪站点。
