## 本周要点

本周最值得关注的是 Trajectory2Gym：它指出“成功的轨迹”不等于“好的训练数据”，只保留在当时可见历史下有依据的决策来做 SFT，在五个尺寸的 Qwen3 上把 τ、τ²、BFCL 三基准均值拉高 17–30 个点。评测侧有三条互相呼应的信号：MCP 故障注入表明模型变大并不会更抗故障、框架级错误处理更关键；Salesforce 的 CRM-Agent-Bench 用逐任务“可执行合约”做严格评分；CXBench 则发现八成“结果正确”的运行其实违反了流程要求。工程侧，StateMirror 在执行前以毫秒级拦截幻觉工具调用，另一项能耗研究提醒：4-bit 量化省的是每 token 能耗，不一定省每个完成任务的能耗。

## 1. Trajectory2Gym：面向工具智能体的“决策有据”组合式交互合成

- 链接：[arXiv:2610.33568](https://arxiv.org/abs/2610.33568)
- 来源 / 日期：arXiv，2026-10-24
- 主题：agent_finetuning · tool_calling ｜ 相关度：**5/5**

**摘要：** 作者认为合格的工具使用训练数据需要两点：覆盖关键的“观测→动作”依赖组合，以及每个被监督的动作都能由智能体当时看得到的历史推出。Trajectory2Gym 围绕训练集中支持不足的组合结构构造可执行交互，只从实际执行中“有据可依”的决策取监督信号，并按结构支持度分配生成量；训练时以整段交互为单位做归一化加权的 SFT。在五个尺寸的 Qwen3 上，τ、τ² 与 BFCL 全部提升，三基准等权均值提升 16.9–29.8 个点，收益集中在后续决策依赖前序观测的有状态多轮交互。暂未见代码。

**可借鉴之处：** 做拒绝采样或轨迹蒸馏时，别只按“最终成功”过滤——逐步检查每个动作是否由当时可见信息支撑，把“蒙对”的步骤剔除或降权，并有意补齐稀缺的多步依赖模式（如先查单据再改状态）。

## 2. MCP 真实故障下的工具调用智能体：规模换不来容错

- 链接：[arXiv:2610.32555](https://arxiv.org/abs/2610.32555) ｜ 代码：[MCP-Injector（GitLab）](https://gitlab.com/uniluxembourg/snt/sedan/papers/mcp-injector)
- 来源 / 日期：arXiv，2026-10-23（NeurIPS 2026 poster）
- 主题：tool_calling · evaluation ｜ 相关度：**5/5**

**摘要：** 作者实现了一个插在 MCP 调用路径上的故障注入中间件，支持永久、瞬时、间歇三种持续性和可复现的故障计划；故障分布依据 1,774 个开源 MCP 仓库中约 5.7 万条 issue/PR 统计校准。实验交叉了 gpt-oss 20B / 120B、三种智能体栈（自研 plan-and-execute、OpenAI Agents SDK、LangChain）与三种注入条件，共 1,350 组。以永久故障为主时任务完成分从 8.08 降到 3.23（满分 10）；120B 在故障下保留的相对得分并不比 20B 高（p=0.96），而不同智能体栈的差异明显，作者结论是框架层错误处理比模型规模更重要。

**可借鉴之处：** 企业接口超时、限流、权限失效是常态——在回归测试里加入按真实分布校准的故障注入，并把重试、降级、报错上报做进 harness，而不是指望换更大的模型来兜底。

## 3. CRM-Agent-Bench：在有状态企业环境中评测工具智能体

- 链接：[arXiv:2610.32004](https://arxiv.org/abs/2610.32004) ｜ 代码：[salesforce-misc/crm-agent-bench](https://github.com/salesforce-misc/crm-agent-bench)
- 来源 / 日期：arXiv，2026-10-23
- 主题：enterprise_agents · evaluation ｜ 相关度：**5/5**

**摘要：** 包含 9 个业务域、36 个能力标签下的 555 个有状态多轮任务。每个任务都配有一份可执行“合约”，检查动作、参数、顺序、回复、目标状态，以及不应被改动的“受保护状态”；只有全部检查都通过才算成功，同时记录覆盖率、延迟与成本。16 个系统的严格成功率在 64.3%–83.6% 之间，头部系统总分接近，但成本和分域可靠性差异很大。数据与代码以 CC BY 4.0 开放。

**可借鉴之处：** “受保护状态”检查非常适合 ERP 场景——除了验证该改的字段改对了，还要验证不该动的记录没被动；可以把这种合约格式直接用作内部 RL 环境的可验证奖励。

## 4. CXBench：受监管客服流程中的流程合规评测

- 链接：[arXiv:2610.25954](https://arxiv.org/abs/2610.25954)
- 来源 / 日期：arXiv，2026-10-19（上期未覆盖）
- 主题：enterprise_agents · evaluation ｜ 相关度：**4/5**

**摘要：** 覆盖 6 个受监管领域、120 个任务，每个任务包含客户请求、工具环境和明确的流程要求；“规则卡”把具体的合规义务映射到可在轨迹中观察的证据。评分把结果合规与流程合规分开：顺序与授权用确定性检查，语义要求交给 LLM 评审。7 个模型共 840 次有效执行中，55.5% 是“假通过”（结果对但流程不合规），占所有结果正确运行的 80.1%；两项都过的只有 13.8%，且加入流程检查后模型排名发生变化。暂未见代码。

**可借鉴之处：** 审批、授权、先核验后操作这类流程约束，只看最终结果的评测会大面积漏判；内部评测与奖励设计都应把“过程合规”单列为一个硬指标。与本期 CRM-Agent-Bench 的合约式评分思路一致。

## 5. StateMirror：执行前检测编码智能体的幻觉工具调用

- 链接：[arXiv:2610.32648](https://arxiv.org/abs/2610.32648)
- 来源 / 日期：arXiv，2026-10-23
- 主题：tool_calling ｜ 相关度：**4/5**

**摘要：** 先分析 4,398 条轨迹，发现一次幻觉工具调用平均（中位数）要多花 3 步、约 2.2 万 token 才能恢复。StateMirror 在 harness 边界拦截动作，用 AST 与命令解析抽取“文件存在”“符号已定义”之类的状态谓词，再对照真实仓库状态校验。在 2,508 个动作上精确率 0.940、F1 0.817，F1 比最强的 LLM 评审高 35.3%，中位延迟从 17.7 秒降到 1.5 毫秒且不耗 token；把检测结果提前反馈给智能体后，超过 95% 的幻觉调用被自行修正，79 个真实任务中执行时间降 15.8%、token 降 11.8%。暂未见代码。

**可借鉴之处：** 企业场景同样可以做“执行前状态核验”：调用前确定性地检查引用的单号、客户 ID、字段是否真实存在，比事后让 LLM 判对错便宜几个数量级。

## 6. SCOPE：只在关键出错步做 on-policy 自蒸馏的智能体 RL

- 链接：[arXiv:2610.38391](https://arxiv.org/abs/2610.38391)
- 来源 / 日期：arXiv，2026-10-28
- 主题：agent_finetuning ｜ 相关度：**4/5**

**摘要：** SFT 预热后，策略回看自己的轨迹，为具体出错步骤生成“事后技能”提示，再只在这些选定的错误步上做自蒸馏，避免整条轨迹级提示带来的偏离信号；辅助更新用有界、带符号的师生系数稳定，另加一个相对成功轨迹的长度奖励鼓励更短完成。Qwen2.5-3B 在 ALFWorld（已见任务）达 97.7%、WebShop 85.2%，分别比 SEED 高 5.9 / 6.3 个点；未见 ALFWorld 任务 89.6%，比 GRPO 高 23.2 个点且交互步数少 46.7%。Qwen3-32B 在已见 / 未见任务上为 99.2% / 94.0%。暂未见代码，且基准偏玩具环境。

**可借鉴之处：** 自蒸馏信号只打在关键错误步上，是对上期[自蒸馏“现实检验”](2026-10-18.md)所指出的增益不稳定问题的一种回应；在工具调用任务上可先用便宜的规则找出错步，再只对这些步加蒸馏损失。

## 7. 量化智能体完成任务的真实能耗

- 链接：[arXiv:2610.32417](https://arxiv.org/abs/2610.32417)
- 来源 / 日期：arXiv，2026-10-23（v2 于 10-26 修订）
- 主题：quantization_inference ｜ 相关度：**4/5**

**摘要：** 作者构建了 29 个带自动判定的智能体任务（6 类，从单答案 SQL 分析到多步仓库修 bug），在 A100 裸机上用 llama.cpp 测量两个开源模型 4-bit 与 8-bit 版本的 CPU+GPU 能耗。4-bit 通常降低每输出 token 的能耗，但是否降低“每完成一个任务”的能耗取决于任务、模型和执行预算（轮数、token、时间上限）；差距来自低比特模型完成任务需要的额外 token，最多可让每任务能耗高出 3.5 倍。暂未见代码。

**可借鉴之处：** 评估量化方案时，以“每成功任务的成本/能耗/时延”为指标，而不是 tokens/s；对多步工具任务，8-bit 或混合精度可能反而更省。

## 8. 多步智能体的工具推荐：找出任务需要的每一个工具

- 链接：[arXiv:2610.23707](https://arxiv.org/abs/2610.23707)
- 来源 / 日期：arXiv，2026-10-16（上期列为待复查）
- 主题：tool_calling · enterprise_agents ｜ 相关度：**3/5**

**摘要：** 一个已部署的网关式工具推荐系统：智能体只看到 3 个固定接口，就能访问约 8,200 个工具，不必把所有工具定义塞进上下文；网关以终端用户自己的凭证执行调用，并按用户对各服务的授权和智能体允许的工具集做检查。在 ToolRet 上，把所需工具全部召回进前 10 的比例比 BM25 高 57%；配对的多步工作流中，首次推荐即覆盖全部所需工具的 Codex 会话占 93%；相对固定 100 个工具的列表，输入 token 在 Codex / Claude Code 下分别降 17% / 40%，14 次运行总成本全部下降、最多 40%，任务完成率不变。偏系统报告，未见代码。

**可借鉴之处：** ERP 动辄上千个 API，“检索式工具暴露 + 网关侧按用户权限执行”既省上下文又满足权限审计；训练数据里也应包含“先查工具、再调用”的两段式轨迹。

## 框架更新

- **TRL v1.17.0**（2026-10-29）/ **v1.17.1**（10-30）：采样用 top-k/top-p/min-p 时，重要性采样改为在实际候选集上归一化，修正此前把 vLLM 重要性比率压向 0 的偏差；Qwen3.5/3.6、Qwen3-Next 等线性注意力混合模型的打包训练得到修复（此前会报错或静默算错）；GOLD 支持跨分词器蒸馏；全组同奖励的 GRPO 组直接跳过前后向；rollout 按 vLLM KV 缓存占用自适应控制并发。**行为/破坏性变更**：AsyncGRPO 默认改用 score centering 新目标并丢弃比率落在 [0.5, 5.0] 之外的 token（`score_centering=False` 可恢复旧目标；作者称 FP8 采样 + bf16 训练可追平 bf16 奖励，生成吞吐约降 15–20%）；开启 vLLM 重要性采样时设置 `top_p<1` 或 `min_p>0` 但未设 `top_k` 会直接报错；移除实验性 TPO 训练器；最低依赖升至 torch ≥ 2.6 等。v1.17.1 只修复 LFM2.5 工具调用参数中括号导致的提前截断。（[v1.17.1 发布页](https://github.com/huggingface/trl/releases/tag/v1.17.1)；v1.17.0 说明据第三方依赖升级 PR 转载整理）
