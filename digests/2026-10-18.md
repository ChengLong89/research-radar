## 本周要点

本周最实用的是 SpecAgent：让小模型逐步起草工具调用轨迹、遇到写操作前停下，再由大模型一次性并行校验整段，在 τ²-bench 上成功率与大模型相差不到 1 个点，而显存流量和墙钟时间约减半。训练侧，WorkForge 与 Tev 分别从真实工作文件和“隐藏世界规格”出发规模化构建可验证环境，而一项 1.2 万 H800 GPU 小时的对照实验提醒：十种自蒸馏方法都没能稳定胜过朴素 GRPO。企业场景上，一个基于真实客服流程的基准显示 Qwen3.5-9B 已能超过部分闭源基线，但不同 LLM 评审之间的一致性只有中等水平（κ≈0.52）。

## 1. SpecAgent：面向工具智能体的轨迹级投机与语义校验

- 链接：[arXiv:2610.21463](https://arxiv.org/abs/2610.21463)
- 来源 / 日期：arXiv，2026-10-15
- 主题：tool_calling · quantization_inference ｜ 相关度：**5/5**

**摘要：** 把投机解码的思想从 token 级提升到“步骤级”：弱模型逐步起草动作，只读类工具调用会真实执行以拿到观测，而第一个会修改环境状态的动作会被扣住。强模型随后用一次并行 prefill 校验整段草稿，保留它认为有效的最长前缀，只修复第一个被拒绝的步骤，因此强模型主要输出简短的判决而不是每一步。在 τ²-bench 上成功率距强模型不到 1 个点，显存流量与耗时约减半；在 AutomationBench、VitaBench 上收回 44–75% 的弱强差距，在 MCP-Atlas 的端云协同设定下强模型生成 token 至多减半。暂未见官方代码。

**可借鉴之处：** 企业智能体可按“只读 / 写操作”给工具打标签，用微调过的小模型跑只读探索、大模型只在写操作前把关——既降成本，也天然形成一道安全闸。

## 2. WorkForge：为长程工作型智能体规模化构建可验证环境（上期复查条目）

- 链接：[arXiv:2610.04906](https://arxiv.org/abs/2610.04906)
- 来源 / 日期：arXiv，2026-10-04
- 主题：agent_finetuning · enterprise_agents ｜ 相关度：**5/5**

**摘要：** 从专家工作流出发，先检索匹配的真实文件组成工作区，再从工作区里抽取可核查的事实，并据此反推出任务指令、解题计划以及程序化 + 语义两类校验器。作者由此构建了约 1.67 万个覆盖 40 个职业领域、60 种文件类型的可验证环境。用其后训练 Qwen3.5-35B-A3B-Base，GDPVal 从 45.5 提升到 73.6，APEX 分数从 5.0 提升到 21.3。代码/数据是否开放页面未说明。

**可借鉴之处：** “先有真实文件、再从文件里抽事实、最后生成任务与校验器”的顺序，可直接迁移到 ERP 单据、报表场景，用于批量生成带可验证奖励的 RL 任务。本条在[上期周报](2026-10-11.md)的检索说明中列为待复查。

## 3. 更多方法，更好的智能体？自蒸馏在智能体 RL 中的现实检验

- 链接：[arXiv:2610.19789](https://arxiv.org/abs/2610.19789) ｜ 项目页：[aim-uofa.github.io/Self-Distillation-AgentRL](https://aim-uofa.github.io/Self-Distillation-AgentRL/)
- 来源 / 日期：arXiv，2026-10-14
- 主题：agent_finetuning ｜ 相关度：**4/5**

**摘要：** 作者在 ALFWorld、ScienceWorld、Search-QA、WebShop 四类环境、三种模型规模上，把十种自蒸馏方法与 GRPO 做了统一对照，共 132 次训练、约 1.2 万 H800 GPU 小时，并在 8 个 rollout 种子上评测。结论很克制：没有哪种方法能在各设定下稳定优于 GRPO；最终分数好看可能掩盖训练过程不稳定；额外训练开销也不一定换来收益。

**可借鉴之处：** 在给智能体 RL 管线叠加新技巧前，先把 GRPO 基线调好、做多种子评测并记录训练曲线稳定性；预算有限时，优先投入环境与奖励质量，而不是追新方法。

## 4. Tev：用稠密进度奖励规模化长程智能体环境

- 链接：[arXiv:2610.18868](https://arxiv.org/abs/2610.18868) ｜ 项目页：[tev-agent.github.io](https://tev-agent.github.io/)
- 来源 / 日期：arXiv，2026-10-13
- 主题：agent_finetuning ｜ 相关度：**4/5**

**摘要：** Tev-Gym 包含 7 个领域、1170 个经过验证的长程任务环境，每个任务都由一个对智能体不可见的“潜在世界”规格渲染而成。作者提出进度势能奖励塑形（PPRS），把任务完成进度转化为逐步稠密奖励，缓解长程任务中奖励稀疏的问题。据作者报告，训练出的 Tev-27B 在 ALE-CM 上 Pass@5 可比肩头部闭源模型，在 Terminal-Bench 子集上也有不俗表现；页面未给出具体数值，代码尚未链接。

**可借鉴之处：** 多步业务流程（如采购到付款）的 RL 训练可以借鉴“隐藏状态规格 + 进度势能奖励”，把阶段性完成情况转为稠密信号，而不是只在终点给 0/1。

## 5. 评测 LLM 作为真实客服技能中的智能体工作流执行器

- 链接：[arXiv:2610.14346](https://arxiv.org/abs/2610.14346)
- 来源 / 日期：arXiv，2026-10-09
- 主题：enterprise_agents · evaluation ｜ 相关度：**4/5**

**摘要：** 作者从真实客服对话记录中挖掘反复出现的工作流，整理成结构化“技能”描述，再用兼容 MCP 的模拟环境生成多轮工具调用对话，零样本评测 17 个模型（含 1.7B–14B 开源模型）。评分同时用 5 个 LLM 评审和一个规则评估器，后者检查工具覆盖、虚构工具调用与无依据陈述。GPT-5.4 大幅领先，Qwen3.5-9B 是 20B 以下最强的开源模型且在所有评审下都超过若干闭源基线；但评审两两之间通过/失败判决的平均 κ 仅约 0.52。

**可借鉴之处：** 把“从历史工单挖工作流 → 生成技能描述 → MCP mock 环境”作为企业智能体评测集的构建流水线；评审环节务必配一个确定性规则检查器，并报告评审间一致性。

## 6. RATED：基于执行动态、感知可靠性的工具检索

- 链接：[arXiv:2610.13889](https://arxiv.org/abs/2610.13889) ｜ 代码/数据：[Elliotes/EcoAgent](https://github.com/Elliotes/EcoAgent)
- 来源 / 日期：arXiv，2026-10-09（CIKM 2026）
- 主题：tool_calling ｜ 相关度：**4/5**

**摘要：** 用一个冻结的双塔编码器（对比学习微调）做语义匹配，再用轻量上下文老虎机根据实时执行反馈对候选工具重排序，从而在工具故障时无需重训即可自适应。配套的 EcoAgent 基准含 5172 个真实工具、21 万余条查询-工具对。相对 ToolLLM 检索器，MRR 相对提升 52.2%；在 30% API 故障的场景下，选中故障工具的比例从 86.2% 降到 2.9%，额外延迟不到 1 毫秒。

**可借鉴之处：** 工具多、上游接口时好时坏的企业环境中，把“近期调用成功率”作为检索重排信号，成本极低却能显著减少无效调用。

## 7. 智能体 LLM 如何决定调用工具？一个由“抑制”塑造的工具调用向量

- 链接：[arXiv:2610.09624](https://arxiv.org/abs/2610.09624v1) ｜ 代码：[XijieGo/MI4ToolCalling](https://github.com/XijieGo/MI4ToolCalling)
- 来源 / 日期：arXiv，2026-10-07
- 主题：tool_calling ｜ 相关度：**3/5**

**摘要：** 作者把长智能体提示压缩成最小对比对，发现仅把执行类动词换成分析类动词（如 write → discuss）就能翻转是否调用工具。基于 500 对提示，他们找到一个对调用决策既必要又充分的方向向量，并用 transcoder 分解说明：分析类动词通过“无需用工具”的特征抑制了脚手架带来的调用先验。该机制在 Qwen、Mistral、Granite 三个家族的七个模型上一致，并能迁移到 τ²-bench 原生多轮轨迹。

**可借鉴之处：** 排查“该调不调 / 不该调乱调”时，可以检查系统提示与用户措辞中的动词倾向；也可考虑用此类激活方向做调用倾向的监控或轻量干预。

## 8. 何时更小更绿色？为智能体任务挑选合适规模的模型

- 链接：[arXiv:2610.19345](https://arxiv.org/abs/2610.19345)
- 来源 / 日期：arXiv，2026-10-14
- 主题：quantization_inference ｜ 相关度：**3/5**

**摘要：** 作者主张按“每个成功完成的任务”而非“每次调用”来衡量能耗、成本和时间，并建模出交叉任务长度：超过该长度后，更小但更不可靠的模型反而更贵、更慢、更耗能。他们先用 Pareto 筛掉没有竞争力的模型，只在仍有取舍时再做加权决策。对 15 个 0.6B–27B 开源模型的实测表明：短任务偏好小模型、长任务偏好大模型，且由单步测量预测的交叉点与实测大体一致。

**可借鉴之处：** 做小模型路由时，按任务步数分桶统计“每成功任务成本”，以此设定路由阈值，而不是只看单次调用的价格。
